## 1. 현상

실행기 기능 개선과 회귀 테스트는 진행되었지만, 핵심 완료율 추정치 **97%**가 반복되었다. 남은 완료 조건은 실제 오프라인 배포 바이너리로 **자연어 요청 → LA 기반 Preview 및 검증 → 명시적 승인 → SQLite 실행 → 결과·감사 조회와 재기동 복구**를 실행해 입증하는 것이었다. 당시에는 주로 라우팅/모의 실행기 테스트를 통과했을 뿐, 최신 배포물의 실제 실행 결과가 없었다.

**97%는 시간·코드량으로 측정된 객관적 수치가 아니라 검증 미완료를 나타낸 내부 추정치였다.** 검증 전 임의로 98%, 99%, 100%로 올리지 않았다.

## 3. 해결 절차

1. GitHub 연결의 `fetch_file(path="apps/ax-flow/hae-integrated.pyz", encoding="base64")` 경로로 **완전한 바이너리 Base64**를 읽었다. 텍스트 디코딩 오류를 피한 것이 결정적 전환점이었다.
2. Base64를 로컬 컨테이너로 이동하여 **원본 파일을 복원**했다. 임시 데이터 전송 매개로 사용자 연결 Google Drive에 임시 Google Doc을 만들었다가 작업 후 **삭제**했다. 고객 데이터/토큰을 담지 않았지만, 이 방식은 민감한 사설 코드에 일반화해서는 안 된다.
3. 배포 파일의 전체 크기, Git blob SHA와 SHA-256, ZIP 내 모듈 및 압축 무결성을 확인했다.
4. 기존 `apps/ax-flow/launch_integrated.py --verify`의 **실제 HTTP/SQLite 7단계**를 실행하고, 실제 오프라인 서버 기동 및 `start_hae.py --verify` 경유 결과를 확인했다.
5. `test_start_hae.py` 13개 테스트를 실행해 실행기 회귀를 확인했다.
6. 검증 결과, 시스템 범위 및 재현 방법을 `apps/ax-flow/ACCEPTANCE-EVIDENCE-20261029.md`에 증빙하고 커밋 `54e5fec1b8fa54986517d566a5293c8d54597586`로 푸시했다.

## 5. 이번 과정에서 실제 반영한 실행기 개선

- `7054295f47cc` — `HAE-Start.cmd`의 `--verify` 인수를 Python 디스패처에 전달.
- `c1a9eedf1d0f` — 이전 SQLite 데이터가 있더라도 임시 합성 환경에서 LA 검증 가능하도록 검증 경로 분리.
- `dc252b22266a` — 일반 실행용 포트·브라우저 인수가 `--verify`에 섞이지 않게 격리.
- 위 기능은 **기존 LA 백엔드의 핵심 코드를 새로 작성한 것**이 아니라, 이미 제공된 실검증 경로에 안전하게 도달하도록 실행기를 고친 것이다.

## 6. 재발 방지 표준 절차 (다음 프로젝트에도 적용)

1. **먼저 완료 기준을 고정:** 기능 추가 수보다 사용자 시나리오의 실제 실행 결과로 정의한다.
2. **이미 존재하는 E2E부터 실행:** 단위 테스트·CI·문서·UI 보완을 먼저 시작하지 않는다.
3. **실행 가능한 배포물/환경을 1순위 확보:** 바이너리 API가 UTF-8을 강제하면 명시적 `base64` 콘텐츠 API 또는 적법한 아티팩트 다운로드를 사용한다.
4. **CI 인프라 실패와 테스트 실패 분리:** `runner_id=0`, `steps=[]`이면 실행 증거 없음으로 기록하고 별도 실행 경로를 찾는다.
5. **임시 매개체 사용 시 위험 통제:** 사설 코드·민감 정보의 외부 업로드를 기본 해결책으로 삼지 않는다. 필요한 경우 승인된 경로만 사용하고 임시 파일은 삭제하며 비밀·고객 데이터는 제외한다.
6. **SHA·OS·Python 버전·PASS/FAIL을 함께 기록:** 이전 커밋의 PASS를 새 커밋에 승계하지 않는다.
7. **완료율 범위를 분리:** '합성 핵심 MVP E2E 100%'와 'Windows 배포·상용 전체 HAE 100%'는 다른 게이트다. 실행 확인 전 퍼센트로 진척을 꾸미지 않는다.

## 7. 남은 게이트

- 실제 Windows에서 `HAE-Start.cmd --verify`, 압축 배포물 `VERIFY-WINDOWS.cmd --no-pause`, NTFS 전용 검사 3종을 **동일한 배포 버전**으로 실행.
- Windows 브라우저 UI, 전체 회귀, 보안·안정성·릴리스 검증.
- OAuth/외부 제공자 연동, DBVORA 복원, 고객 파일/업무 시나리오 등 **전체 상용 HAE 제품** 게이트 별도 진행.

**정리:** 가장 큰 실패는 개발이 미완성이었던 것이라고 단정한 것이 아니라, **검증 대상 바이너리를 실행하지 못한 상태로 주변 작업을 반복한 운영 순서**였다. 우회한 것은 검증 기준이 아니라 **바이너리 전달 경로**였으며, 성공 판정은 실제 로컬 HTTP·SQLite 실행을 근거로 한다.
