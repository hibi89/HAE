# HAE 생태계 공식 정본 — Humanized Automation Ecosystem
> OWNER DECISION / 2026-10-28 KST · status: **TARGET ARCHITECTURE (NOT IMPLEMENTATION CLAIM)** · source of truth: private `hibi89/HAE@main/docs/ECOSYSTEM_CANONICAL.md`
>
> 새 채팅·작업 브랜치·총괄 에이전트는 이 문서의 **고객 사용 흐름·4대 필수 요소·제품 경계**를 최신 사용자 명시 결정으로 적용한다. 이전의 "n8n 우선 런타임" 및 "SOVIA 선택형/향후 고려" 문구와 충돌하면 본 문서를 우선한다. 기존 실행 코드/제품별 테스트 상태/대회 규정까지 이 문서가 덮어쓰지는 않는다.

## 0. 한 문장 제품 정의

**HAE = 고객이 자연어로 자동화를 요청하면 → LA(Lightning Azent)가 실행 가능한 플로우를 자동 설계·배치하고 → HAE가 필요한 고객 정보와 승인 사항을 단계별로 받아 쉬운 실행 가이드를 제공하고 → 테스트를 거쳐 LA가 승인된 작업을 실제 실행하고 → SOVIA가 요청·계획·권한·행동을 안전성 검증/감사하며 → DBVORA 연동으로 필요한 업무 데이터를 DB화하고 DB 구조·상태·보존을 관리하며 → HAE가 최종 결과와 실행·감사·데이터 상태를 한곳에 제시하는 통합 생태계.**

**선택 기능을 더하거나 별도 상품과 결합하는 것은 이 기반을 완성한 뒤다.** 새로운 제품이 합류해도 HAE/LA/SOVIA/DBVORA의 핵심 소유 책임을 임의로 대체하거나 누락하지 않는다.

## 1. 네 가지 필수 제품과 책임

| 구성 | 공식 역할 | 소유하지 않는 책임 |
|---|---|---|
| **HAE — Humanized Automation Ecosystem** | 고객과의 유일한 통합 UX: 자연어/템플릿 접수, 고객 정보 단계별 안내, 권한 요청과 승인 UX, 플로우 미리보기, dry-run/실행 제어, 통합 결과·DB/감사 대시보드 | 원시 모델 텍스트를 바로 실행하지 않음; 임의로 비밀을 수집하거나 보안 정책 우회하지 않음 |
| **LA — Lightning Azent** | 자체 개발한 실행/플로우 엔진: 형식화된 IR 및 플로우 구성·검증, 노드/스텝 연결, 데이터 이동/변환, 실제 데이터베이스 read/write, 스케줄, 실행/재시도/복구, 단계별 실행 영수증. **실제 액션의 유일한 집행자** | SOVIA 감사 결과를 스스로 인증하지 않음; DBVORA 자산·백업 관리 대체하지 않음 |
| **SOVIA Sovereign** | **HAE의 필수 위험/행동 감사 구성**: 실행 계획 권한·데이터 이동 점검(목표), 최소 권한/고위험 승인 정책 대조(목표), 실제 LA 실행 기록·원본 요청·승인 내용과 사후 대조, 사건/불명/증거·위험 리포트 | 플로우 실행/고객 비밀 관리/DB 생성 직접 집행하지 않음. 독립 제품으로도 유지 |
| **DBVORA** | **HAE의 필수 DB화·DB 운영 구성**: LA가 만든/적재한 고객 업무 DB를 연결해 DB 구조(테이블·컬럼·관계), 크기/출처/상태/자원 메트릭을 실제 지원 범위에서 가시화; 승인된 안전한 백업·검증 복구·아카이빙; 독립 제품·저장소 유지 | 고객 업무 데이터를 자기 판단으로 이동하거나 임의 SQL 실행/외부 작업을 자동화하지 않음. LA 실행 엔진 대체하지 않음 |

### DB화는 실제 데이터 저장까지 포함한다
- 고객의 데이터 기반 자동화는 **LA 업무 데이터 어댑터가** 유효성 검사·정규화·매핑을 수행하고 고객이 승인한 **업무용 SQLite 등의 저장소에 실제 레코드를 생성/갱신/조회**해야 한다.
- **DBVORA가** 그 업무용 DB를 연계해 자산 목록·스키마/FK·크기·변경/저장 상태·복원 가능한 백업을 관리한다. 단순 HTML 맵만으로 "DB화 완료"라 부르지 않는다.
- DB 없는 이메일 알림 같은 작업에 불필요한 업무 DB를 강제 생성하지 않는다. 그러나 **전체 HAE 제품의 완성 판정은 DB 사용 시나리오를 통과하고 DBVORA가 제품에 연동된 경우에만** 허용한다.
- **LA 런타임/영수증 SQLite**, **고객 업무 DB**, **SOVIA 감사 기록/SQLite**, **DBVORA 관리/백업 메타데이터**는 목적과 접근 권한을 분리한다. 고객 원본은 원 소유 위치를 유지한다.

## 2. 고객에게 보이는 단일 흐름 (필수)

1. **요청 접수 — HAE:** 고객이 자연어로 "무엇을 자동화할지" 적고 필요한 경우에만 파일을 첨부한다. 고객이 JSON/노드를 직접 편집하지 않는다.
2. **플로우 생성 — LA:** HAE의 계획 수립 계층이 요청을 해석하고 LA의 버전 있는 **선언형 IR**로 플로우를 구성/배치한다. LA는 지원 기능·스텝·연결·스키마·작업 한도를 검증한다. 지원 불가 작업은 설명하고 중단한다.
3. **실행 전 감사 — SOVIA 목표 기능:** 외부 송신 대상, 파일/DB 접근, 필요 API 권한, 파괴적/재정적 행동 및 누락된 승인·예상 위험을 검사해 HAE에 전달한다.
4. **단계별 준비 — HAE:** 실행에 꼭 필요한 정보만 순서대로 받고 설정/권한 연결 방법을 쉬운 한국어로 안내한다. 토큰/OAuth는 보호된 브로커에서 직접 취급하고 SOVIA/모델 로그에는 원문을 남기지 않는다. 고객의 승인 범위는 플로우 버전과 함께 기록한다.
5. **검증 — LA + HAE:** 실제 입력 구조·타입·한도·권한 검사, 가능한 범위의 dry-run/합성 테스트, 고객이 확인하는 실행 미리보기. 위험·실패 사유를 고객 언어로 보여준다.
6. **실행 — LA:** 명시적으로 승인된 작업만 수행. 실행 중 고위험 행동은 버전 고정된 권한/승인 범위 내인지 **LA가 강제**하고, 계획 외 행동·불명확한 승인·감사기 연결 실패 등 고위험 상태는 안전하게 중지하거나 재승인을 요청한다. SOVIA의 정책 검사 인터페이스는 향후 통합; **SOVIA 선택 해제 여부와 관계없이 LA의 기본 권한 게이트를 없애지 않는다.**
7. **DB화·DB 관리 — LA + DBVORA:** 데이터가 필요한 작업은 LA가 고객 허가 범위에 맞게 데이터 구조화/저장/재실행 영수증을 남긴다. DBVORA는 승인된 업무 DB의 구조·상태·크기·출처를 보여주고 검증된 범위에서만 백업·복원을 수행한다. HAE가 이를 한 화면에 합친다.
8. **행동 사후 감사 — SOVIA:** 최초 목적, 승인, 플로우 해시, LA의 관측 실행 기록, 외부 영수증이 있으면 그것을 대조해 사실/정책 위반/확인 불가능한 범위/조치 권고를 리포트로 제공한다. 관측되지 않은 일을 '안전'이라고 단정하지 않는다.
9. **결과/운영 — HAE:** 성공·실패·부분 성공, 고객이 확인할 작업, 감사 보고서, DB 상태·복구 옵션, 재실행/일정 관리 정보를 단일 UX로 제공한다.

## 3. 경계와 연동 규약 (제안 — 현재 구현 완료 아님)

**원칙:** 각 제품은 독립 버전·저장소·권한 경계·테스트를 유지한다. HAE는 통합 UX/오케스트레이션을 맡으며, LA는 실행 원천, SOVIA는 감사 원천, DBVORA는 DB 상태/보존 원천이다.

| 경계 | 계약에 필요한 정보 | 엄격한 원칙 |
|---|---|---|
| HAE → LA | user_intent_ref, normalized plan/IR version, step parameters, scoped approval/limit, run_id | 원문 프롬프트를 직접 실행 금지; 지원하지 않는 스텝 차단 |
| LA → SOVIA (계획) | plan_digest/version, tool types, requested scopes, destinations, planned side effects | **신규 plan-risk API는 설계안**, 지금 사후 감사 엔진으로 실시간 차단 가능하다고 주장 금지 |
| LA → SOVIA (실행) | agent/run/step IDs, timestamps, policy version, decision/receipt references, outcome, evidence coverage | 로그와 서명 없는 해시만으로 외부 행동의 사실성·완전성 증명 불가 |
| LA ↔ DBVORA | user-approved asset ID, versioned schema/inventory, source provenance, backup/restore receipt | LA의 업무 DB 쓰기와 DBVORA의 관리 작업 권한 분리; DBVORA 실 API에만 바인딩 |
| SOVIA → HAE | finding ID, severity/rationale, evidence/ref/unknown, recommended action | 거짓 안전인증/법적 인증 금지; 고객에게 설명 가능한 결과 |
| DBVORA → HAE | asset map, tables/columns/FK, observed size/health, validated snapshot status | 무검증 리소스·복원 기능을 구현/성공으로 표시 금지 |

실제 통신 포맷, 스키마 이름, 버전, 쓰기 승인 UX, 배포·기밀 경계는 구현 시 각 총괄이 별도 테스트와 합의로 확정한다. 본 문서의 단계명은 가상 계약 예시이며 이미 배포된 API가 아니다.

## 4. 전체 HAE의 완료(Definition of Done)

- **사용자 완성 흐름:** 비개발자가 자연어만으로 실제 지원되는 최소 1개 업무 자동화를 생성·단계별 고객정보 제공·승인·dry-run·실행·상태 확인할 수 있고 수동 JSON/노드 작업이 없어야 한다.
- **LA:** 실제 전체 체크아웃에서 단독 테스트와 원래 HAE 회귀 테스트 통과, 지원 시나리오의 실행·스케줄/재시작·중복 쓰기 방지와 실행 영수증 검증.
- **SOVIA:** 원본 요청/승인/플로우/LA 관측 실행을 연계한 감사 보고서 생성; 기본 감사 MVP와 이후의 계획·위험 차단은 별개 시험·상태 관리. 중요한 실행 안전은 LA에서도 강제.
- **DB화:** LA가 합성 또는 허가된 실제 업무 데이터로 업무용 DB를 구성·적재·조회하는 재현 가능한 end-to-end 시나리오가 있어야 한다. DBVORA에서 해당 자산의 실제 테이블·컬럼·관계·측정 가능한 크기/상태를 확인하고, 제품이 약속하는 지원 범위의 안전한 백업·독립 복원을 검증한다.
- **통합:** HAE 고객 화면에서 위 4구성 요소의 실제 결과·오류·감사·DB 상태를 볼 수 있어야 한다. Windows, 경계 실패, 권한 부족, 타임아웃, 수집 실패, 데이터 복구 거부를 검증한다.
- **출시/판매:** 코드/합성 CI 성공 ≠ 실 고객 가동/상용 출시. 허가된 환경, 개인정보/비밀, 라이선스, 취약점/복구, 매뉴얼/지원, 고객 승인 및 실제 데이터 처리 권한을 추가 확인한다.

**3일 MVP ≠ 생태계 최종 완성.** 초기는 하나의 사용 흐름을 먼저 작동시키고, 그다음 4구성의 확인 가능한 연결을 채운다. 신규 GUI 미관·과다 문서·일반 목적 연동 확대는 핵심 기능과 E2E 검증 이후다. 해커톤 공식 제출 마감과 별도 저장소의 소유권/승인 게이트를 변경하지 않는다.

## 5. 확장 규칙 — '여기에 다른 것을 섞는다'

- 네 필수 구성의 외곽에 **확장 어댑터/독립 제품**을 연결한다. 추가 기능은 목적, 데이터 흐름, 권한, 비용, 사용자 편익 및 인터페이스 버전으로 결정한다.
- **REA_APP**: 다른 앱의 기술 분석을 위한 별도 연구/개발 도구. HAE의 런타임, 중앙 오케스트레이터, SOVIA 또는 DBVORA가 아니다.
- **코드체커 (Code Checker; 과거 이름 CODE COUNCIL 폐기)**: 코드 보안/성능/아키텍처/테스트/신뢰성/자원/유지보수/비용 검토 독립 제품. 향후 코드 생성 파이프라인의 선택형 검사기로 연동 가능; 4필수 코어를 대체하지 않는다.
- **SMAX, RAG_STUDIO 등**: 향후 사용자 결정으로 별도 서비스·템플릿·데이터 어댑터로 연결 가능. 실제 결합·출시·유료화 승인 전까지 구현됐다고 기록하지 않는다.
- **n8n**: 과거 참고/연구 대상 및 향후 **외부 호환 어댑터 후보일 뿐, HAE의 실행 엔진 또는 SOVIA 통합 1순위가 아니다.** 공식 우선순위는 LA → SOVIA/DBVORA → 추가 기술.
- 별도 라이선스, 실제 고객 데이터, 외부 API/OAuth, 유료 계정, 공개 배포, DB 파괴적 변경 등은 사전 검토·명시 승인 없이 실행하지 않는다.

## 8. 2026-10-29 사용자 승인 — HTML 로컬 UX와 단계별 데스크톱 실행

> OWNER DECISION / 2026-10-29 KST. 현재 채택한 사용자 경험과 구현 순서를 기록한다. **설계 결정이지 구현·테스트·출시 완료가 아니다.** 기존 HAE·LA·SOVIA·DBVORA 필수 책임, 허가·보안 경계는 유지한다.

### 목표 UX 및 실행 원리

- 고객은 **HTML/CSS/JavaScript 웹형 HAE 화면**에서 자연어/템플릿 입력, 자동화 계획 확인, 필요한 정보·권한 제공, 명시적 승인, 실행 결과·감사/DB 상태 확인을 한다.
- HAE Python 백엔드는 로컬 UI/API, 요청 해석·검증된 선언형 IR 계획·승인·통합 표시를 맡는다. **독립 Python 엔진 Lightning Azent(LA)** 는 화면 없이 승인된 계획을 실제 실행하고 상태·영수증을 제공한다. SOVIA 감사, DBVORA DB 가시화/복구는 기존 공식 정본에 따라 필수 통합이다.
- 브라우저는 정적 HTML을 file:// 경로로 직접 렌더링할 수 있지만 **HTML만으로 Python/LA를 실행하지 못한다**. JS 모듈·fetch·파일 접근 또한 file:// 보안 제약을 받는다. 첫 구현은 HTML도 제공하는 로컬 HTTP 서버 + Python/LA 방식이 적절하다.
- '웹처럼 보임'은 공개 인터넷 SaaS라는 뜻이 아니다. localhost(127.0.0.1)에서 고객 PC 안의 실행을 제공할 수 있다.

### 권장 4단계 로드맵

1. **A — 즉시 우선: 브라우저형 로컬 MVP.** 기존 HAE HTML/JS UI → 127.0.0.1 Python HAE API → 별도 LA 패키지/버전 검증 → 계획 preflight → 원본/승인 검증 → 합성 SQLite 실행 → 결과/감사 확인. 실제 브라우저 E2E와 기존 HAE/LA 회귀를 통과해야 통합 PASS.
2. **B — A 이후: 더블클릭 실행기.** 바탕화면 HAE 아이콘/경량 launcher가 로컬 Python 서비스 시작, 기본 브라우저 열기, 정상 종료·오류 처리·포트 충돌·중복 실행 관리. 사용자가 콘솔 명령을 직접 입력하지 않도록 하지만 이 단계는 아직 제품 설치 완료가 아님.
3. **C — 선택형: 백그라운드·시스템 트레이.** 고객이 명시적으로 켠 스케줄만 UI 창과 분리된 실행 프로세스에서 처리하고, 트레이에서 실행/정지/상태를 관리. 프로세스 충돌·재시작·중복 실행·승인과 권한 테스트 필요. PC가 꺼져 있으면 로컬 스케줄 불가. 창 닫힘과 서비스 종료 정책은 사용자에게 분명히 표시.
4. **D — 최후순위: 전용 데스크톱 앱 창.** Tauri/기타 WebView/IPC 등은 필요할 때 성능·용량·설치/관리 비용을 비교해 도입. 현재 HTML UI와 LA/Python 엔진은 최대한 재사용하고 전체 엔진을 JS로 다시 작성하거나 Electron/Tauri를 선도입하지 않는다.

### 대안 비교 및 선택

- 정적 file:// UI + 직접 IPC 접근: HTTP 서버를 생략할 수 있지만 Python 실행을 호출하는 네이티브 호스트와 배포 구조를 초기에 추가해야 한다.
- **HTML UI + localhost HTTP + Python/LA: 우선 채택.** 현행 HAE 코드와 로컬 E2E를 재활용하고 백엔드 책임을 명확히 유지한다. '서버 없음' 그 자체를 목표로 최적화하지 않는다.
- 설치형 전용 컨테이너/백그라운드 서비스는 A의 실제 E2E가 성공한 뒤 필요한 경우 추가한다.

### 필수 구현·안전성 조건

- 로컬 bind, Host/Origin/CSRF, 권한·승인·한도·비밀 저장 분리 및 비허가 외부 송신 금지를 유지한다.
- HAE의 계획/실제 입력 스냅샷·파일 해시·승인 해시와 LA 실제 실행 간 일치성을 검증한다. 이 계약이 불명확하면 LA 쓰기 연동은 fail closed, 모의 테스트만으로 성공 주장 금지.
- LA는 독립적으로 테스트/버전 관리하고 기존 HAE 실행 경로를 무단 삭제하지 않는다. SOVIA와 DBVORA의 전체 제품 필수 통합도 축소하지 않는다.
- 오프라인 합성 1개 핵심 시나리오 먼저. 기능·정확성·실패/복구 검증 후 UX와 패키징으로 전진한다. 외부 API/OAuth·실고객 데이터·공개 배포·유료 실행·자동 OS 상주는 별도 승인 대상이다.
- 본 기록은 설계 정본의 추가이며 개발 브랜치 병합·소스 수정·프로그램 실행을 승인하거나 수행한 것이 아니다.
